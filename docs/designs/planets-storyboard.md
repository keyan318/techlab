## Problem Statement

Astro (the mascot/AI teacher) exists in chat and as art assets, but has no in-product origin story. New students land on a dashboard of placeholder nodes with no narrative reason to start the Programming course. This feature adds `/planets`: a full-screen, one-panel-at-a-time comic storyboard (Instagram Stories format) telling Chapters 1–2 of Astro's crash-landing on Codexia, ending in a CTA that unlocks the Programming (HTML/CSS/JS) course.

## What Makes This Cool

The Stories format is the one narrative UI teens already know without a tutorial — using it for course onboarding means zero learning curve and full-screen immersion. And the story's moral ("structure before decoration") is literally the pedagogical thesis of learning HTML before CSS before JS: the story teaches *why* the course is ordered the way it is.

## Constraints

- Chapters 1–2 only: crash-land → fail to build twice → realize structure comes first → decide to build properly → CTA. Astro solo; no other characters or chapters.
- Match existing cosmic design language: `--void #06061a`, glass surfaces (`rgba(123,142,220,.07)` + `rgba(150,170,255,.18)` border), Space Grotesk / Inter / Space Mono, accent `#73b6ff` (as in `resources/views/student/planets/programming.blade.php`).
- Self-contained Blade idiom (Approach A) — the app uses no Vite/build-step assets anywhere (zero `@vite` usage); views inline their CSS/JS.
- Auth-gated like every student route (guests → `route('login')`).

## Premises (all confirmed this session)

1. **No course-unlock system or progress table exists** (verified against all 7 migrations). The `'locked'`/`'completed'` strings in `StudentController` are placeholder decoration. This feature creates the smallest real version of unlock persistence rather than pretending to extend something.
2. **Panels are code, not DB rows** — fixed authored content belongs in a PHP config array (`image` path + `caption` + chapter grouping). No admin UI exists that would justify a table.
3. **Persistence decision (D5):** minimal real persistence — `users.storyboard_seen_at TIMESTAMP NULL` + new `course_unlocks` table (`id`, `user_id` FK, `course_slug`, `unlocked_at`, UNIQUE(`user_id`,`course_slug`)). Session-only was rejected (lost on logout, dead end for dashboard); generic polymorphic progress system rejected (3x scope, zero additional consumers today).
4. **Navigation (D6):** full Stories convention — right/left tap-click zones, ←/→ arrow keys, touch swipe, top progress bars, Esc exits.
5. **Seen semantics (D7):** `storyboard_seen_at` written when final panel is reached (skip-to-end counts); course unlock written ONLY on CTA click. Two separate signals ("watched" vs "enrolled").
6. **Route:** `/planets` as specified. Coexists with `/student/planet/{slug}` (overview pages): the storyboard is the story intro; the planet page is the post-unlock destination.
7. Web landscape search skipped by user choice (D8) — Stories interaction pattern is settled knowledge.

## Approaches Considered

- **Approach A: Self-contained Blade (CHOSEN)** — StoryboardController + panels config array + one self-contained view (inline CSS/JS) + migration + feature tests. Effort M (human ~3 days / CC ~45 min — the panel art is the real cost). Completeness 8/10.
- **Approach B: Componentized + model layer** — REJECTED for now: Vite assets, `CourseUnlock` model, typed Panel DTO. Cleanest if more stories come soon, but nothing else consumes that machinery today; YAGNI. Revisit when a second story/chapter ships.
- **Approach C: Runtime-generated comic art via LocalComicProvider** — REJECTED: provider was built for one-off analogy gags; panel-to-panel character consistency would be a gamble, and story quality is the product here.

## Recommended Approach

**Approach A.** Files:

```
routes/web.php                                  +3 routes
app/Http/Controllers/StoryboardController.php   show() / seen() / unlock()
app/Models/User.php                             + 'storyboard_seen_at' in #[Fillable] + datetime cast
config/storyboard.php                           chapters -> panels (image, caption)
database/migrations/2026_08_21_..._storyboard_state.php
resources/views/student/storyboard.blade.php    viewer: inline CSS + ~200 lines vanilla JS
resources/views/student/studentOnboarding.blade.php   + "Watch Astro's story" entry card/link
public/planets/panels/*.svg                     hand-authored panel art (scene backdrops + Astro composites)
tests/Feature/StoryboardTest.php                gates, idempotency, guest POSTs
```

Routes (auth mechanism: controller-level `Auth::check()` → `redirect()->route('login')`, matching `PlanetController::show` — no middleware stack exists in this app):
- `GET /planets` → `StoryboardController@show` (name `planets.show`) — guests redirected to login; teachers bounced to `teacher.dashboard` (matching `StudentController` idiom); renders viewer with panels from config.
- `POST /planets/seen` → `seen` (name `planets.seen`) — guests get the same login redirect; sets `storyboard_seen_at` once via Eloquent update (fillable added above), idempotent by null-check; returns JSON `{ok: true}`.
- `POST /planets/unlock` → `unlock` (name `planets.unlock`) — a plain `<form method="POST">` with `@csrf` (no fetch): inserts via `DB::table('course_unlocks')->insertOrIgnore(['user_id' => …, 'course_slug' => 'programming', 'unlocked_at' => now()])` so a double-click race hits the unique constraint as a silent no-op instead of a 500, then 302-redirects to `/student/planet/programming`.

Entry point: the dashboard (`studentOnboarding.blade.php`) gets one "Watch Astro's story" card linking to `/planets` — without it the route is unreachable except by typing the URL.

Panel data shape (config):
```php
'chapters' => [
  ['title' => 'Chapter 1 · The Landing', 'panels' => [
      ['image' => '/planets/panels/01-crash.svg', 'caption' => '...'],
      // ...
  ]],
  ['title' => 'Chapter 2 · Nothing But Ground', 'panels' => [...]],
]
```
Final panel carries `cta => true`; the viewer swaps nav UI for the CTA button there.

Viewer behavior: progress bars per panel (chapter-grouped), tap zones (right 55% next / left 45% back), keydown ←/→/Escape (Esc exits to `route('student.dashboard')`), touch swipe ≥48px threshold, `100dvh` height with safe-area insets, captions in bottom third. Every visit starts at panel 1 — including users who already saw it (the story is ~90 seconds and a Skip button jumps to the end); `storyboard_seen_at` is written when the final panel is reached, per D7. The `seen` POST is a fire-and-forget `fetch` carrying `X-CSRF-TOKEN` from a meta tag; the CTA is a normal form POST (see routes above).

Art budget (honest version): exactly two usable poses exist today — `public/videos/astro-transparent.png` (full body) and `astro-head.png`. Panel variety comes from SVG scene backdrops, camera crops, and scale changes rather than new character poses. ~8 panels total. This is why Approach C was rejected — and it's the main real cost here: effort is M (human ~3 days / CC ~45 min), not S.

## Success Criteria

- The dashboard shows a "Watch Astro's story" entry that reaches the viewer (the route is discoverable, not just typed).
- Guest at `/planets` → redirected to login; authed student sees full-screen viewer at panel 1; teacher → bounced to their dashboard.
- All four navigation inputs work (tap zones, arrows, swipe, Esc); progress bars reflect position.
- Reaching the final panel writes `storyboard_seen_at` exactly once across repeats.
- CTA click inserts one `course_unlocks` row and lands on Programming City; a double-click or repeat visit inserts nothing and never 500s (`insertOrIgnore`).
- Unauthenticated POSTs to `/planets/seen` and `/planets/unlock` get the login redirect, not a 500 — covered by feature tests alongside seen/unlock idempotency.
- Feature tests pass; pre-existing test suite state unbroken (9 passing Astro tests remain green).
